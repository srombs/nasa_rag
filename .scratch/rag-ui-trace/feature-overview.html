The intended visitor experience

While the search runs

See the active stage and expand completed steps to inspect the query plan, passages, rankings, and relevance reasons. Reranking reports progress after each validated candidate.

Stage updates arrive as the work happens. The whole answer arrives at the end.

When the search ends

Read the answer with its existing citations and warnings. Inspect stage durations, models, recorded calls, available token usage, and estimated costs.

If observation ends early, keep received results and distinguish an actual failure from an unknown outcome.

These are the feature’s intended website behaviors. Backend payloads support them; the production frontend is outside this repository’s ticket set.

02Embed query

See the requested embedding model and the vector’s dimension count. The embedding vector itself is not exposed. Ticket 02 · built

03Semantic search

Inspect up to 30 passages selected by semantic similarity, including their text, references, ranks, and native similarity scores. Ticket 02 · built

04Keyword search

Inspect up to 30 keyword-search passages with their native ranks and BM25 scores. Semantic and keyword scores use different scales. Ticket 02 · built

05Combine rankings

See up to ten combined candidates, their reciprocal-rank-fusion scores, and contributing ranks from each search. Inspection limits do not change the underlying retrieval. Ticket 02 · built

06Rerank evidence

Follow one update per validated candidate, with a relevance score and reason. Progress is in evaluation order; the completed stage supplies the final ranking. Ticket 03 · built

07Generate answer

Inspect the ordered context references supplied to generation. The final answer is delivered after the citation reference check, without answer-token streaming. Tickets 01 + 03 · built

08Check citation references

See whether answer references match the supplied context: valid references, a warning, or no citations. This checks reference membership, not factual accuracy. Ticket 03 · built

Ticket 01 supplies stage lifecycles. Ticket 04 adds per-stage and overall metrics. Retrieved passages are candidates, not guarantees that a claim is proven.

Frontend acceptance

Rollout order: finish backend verification, deploy the additive backend capability, verify the real proxy path, then enable the frontend flow. Backend tests alone do not prove that visitors receive live updates.

Read the results accurately

  • Search scores are native to each method, not answer-accuracy percentages.
  • Costs are estimates. Missing usage stays unknown; a known subtotal may be incomplete.
  • A deadline or disconnect does not establish that model work stopped.
  • HTTP 200 or end-of-stream alone does not establish success; the terminal event determines the observed outcome.

Feature boundaries

  • Whole-answer delivery; no answer-token streaming.
  • Existing search and citation behavior; no new factual-verification classifier.
  • Flow state lives in the current page; no saved history, replay, or reload recovery.
  • Manual retries only; each is a fresh ordinarily limited request.
